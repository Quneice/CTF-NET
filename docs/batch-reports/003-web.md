## 3. 冒烟验收暴露并修复的 1 个真实缺陷

**jwt-decode 的「伪造签名」是空壳**(localHandlers.ts `local.jwt`):表单 schema 提供 action=forge 单选与「签名密钥(HS256)」密码框,但处理器无条件只做解码,密钥与 action 被忽略 —— 违反「不伪装成可用」原则。修复:forge 分支保留用户粘贴的 header/payload 段,用 `crypto.subtle` HMAC-SHA256 重新签名并返回完整 token;缺密钥/缺段时抛错。验证:篡改 payload 加 `role:admin` 后 forge,签名与 Node `crypto.createHmac('sha256', secret)` 独立计算结果一致(不同实现交叉验证);缺密钥分支确认抛错。

该缺陷为批 3 范围内工具(计划表 #1「已实现」)的全链路问题,由「2 个已实现走全链路」验收暴露,按「先审计后修复」原则在本批修复。

## 4. 剩余风险

1. **jwt forge 依赖 WebCrypto**(`crypto.subtle`):需安全上下文;Wails 的 dev(localhost)与生产(wails.localhost,Chromium 视为可信)均满足。同文件 `hashData` 已使用同一 API,约束一致,无新增风险面。
2. **forge 语义为「原样重签」**:不改 header/payload 内容、不降级 alg、不做 none/爆破/角色模板 —— 这些变体由占位工具 jwt-none / jwt-brute / jwt-forge / jwt-role 覆盖,本批不越界实现。
3. **重名组区分度**:两工具同属 web.upload,分类前缀相同(「文件上传」),名称级区分目前靠描述行;计划原文「重名『文件上传绕过』2 个在此批(只记录,阶段 4 处置)」,改名留待阶段 4。
4. **ToolCard 分类前缀为全局视觉增量**:附加验收要求的共享组件改动,影响全部卡片(批 0/1/2 工具亦显示前缀)。为纯增量一行,truncate 防溢出,构建通过;桌面端视觉复核建议手动确认一次。
5. **输出区 chip 未做 headless 渲染**:ToolPage 依赖 wails 适配器与 zustand 存储,node vm 中渲染成本高;chip 逻辑(状态推导)与徽章/横幅同源且已被真实渲染断言覆盖,JSX 分支经 tsc/build 验证。建议 `wails dev` 手动打开任一占位工具提交一次复核。
6. **19 个 SSTI 后端占位提交依赖 Go 后端在线**:realBackend task 在未联调环境下提交会走错误态(徽章/横幅/chip 均已标注占位,不伪装可用);与批 1 的 jndi 同类工具行为一致。
7. **php-unserialize 无 inputSchema**:专用工作区自建表单(PopChainEditor),不走 DynamicForm;工具定义中 inputSchema 缺省为既有设计,本批记录不补。
8. **40 个前端占位工具的 mock 结果**仍为 mockResult 生成器(参数回显等形态匹配数据),真实实现留待后续批次(与 inventory 状态一致)。
